## 2. 历史动机与发展脉络

《微服务架构》是 软件架构 领域的重要主题。要真正理解它，需要先了解它解决的问题与演进过程。

软件架构是系统的“骨架决策”：组件划分、交互方式、非功能属性（性能、安全、可维护性）；架构师职责是权衡与演进。
架构风格演进：单体 -> 分层 -> SOA -> 微服务 -> 云原生（网格/Serverless）；没有银弹，风格是权衡。
方法论：4+1 视图（逻辑/开发/进程/物理+场景）、C4 模型（Context/Container/Component/Code）、ADR 记录决策。

回到本文主题：微服务架构 的提出与成熟，正是上述技术背景下的必然产物。早期实现往往以简单可用为目标，随着工程规模扩大，社区逐渐沉淀出标准做法与最佳实践；理解这一脉络，可以帮助读者判断“为什么文档中的推荐写法是现在这个样子”，也能在遇到历史遗留代码时准确识别其设计年代与取舍。

#### 原文精读（完整保留）


#### 1. 微服务概述

##### 1.1 核心特征

| 特征     | 说明                     |
| :------- | :----------------------- |
| 服务自治 | 独立开发、部署、运维     |
| 单一职责 | 每个服务聚焦一个业务能力 |
| 去中心化 | 数据和治理去中心化       |
| 技术异构 | 各服务可选择不同技术栈   |
| 弹性设计 | 故障隔离，优雅降级       |

##### 1.2 微服务 vs 单体

| 维度       | 单体     | 微服务   |
| :--------- | :------- | :------- |
| 部署       | 整体部署 | 独立部署 |
| 扩展       | 整体扩展 | 按需扩展 |
| 技术栈     | 统一     | 异构     |
| 故障影响   | 全局     | 局部     |
| 开发效率   | 小团队高 | 大团队高 |
| 运维复杂度 | 低       | 高       |

#### 2. 服务拆分

##### 2.1 拆分策略

| 策略       | 说明           | 示例                 |
| :--------- | :------------- | :------------------- |
| 按业务能力 | 围绕业务功能   | 用户服务、订单服务   |
| 按子域     | DDD限界上下文  | 商品子域、支付子域   |
| 按事务     | 事务边界       | 跨事务拆为不同服务   |
| 按变更频率 | 独立变化的拆开 | 核心功能 vs 辅助功能 |

##### 2.2 拆分原则

| 原则       | 说明                   |
| :--------- | :--------------------- |
| 高内聚     | 相关功能放在同一服务   |
| 松耦合     | 服务间依赖最小化       |
| 独立数据   | 每个服务有自己的数据库 |
| 有界上下文 | 明确的服务边界         |

#### 3. API网关

##### 3.1 网关职责

```
客户端 → [API网关] → 服务A
                  → 服务B
                  → 服务C
```

| 职责     | 说明               |
| :------- | :----------------- |
| 路由转发 | 请求路由到后端服务 |
| 认证授权 | 统一身份认证       |
| 限流熔断 | 流量控制和保护     |
| 协议转换 | REST ↔ gRPC        |
| 聚合裁剪 | 响应聚合和字段裁剪 |
| 日志监控 | 统一日志和指标采集 |

##### 3.2 网关模式

| 模式     | 说明                 | 适用场景 |
| :------- | :------------------- | :------- |
| 单一网关 | 一个网关处理所有请求 | 小规模   |
| BFF网关  | 每种客户端一个网关   | 多端适配 |
| 网关网格 | 每个服务一个Sidecar  | 服务网格 |

#### 4. 服务发现与通信

##### 4.1 服务发现

| 模式       | 说明               | 工具           |
| :--------- | :----------------- | :------------- |
| 客户端发现 | 客户端查询注册中心 | Eureka、Nacos  |
| 服务端发现 | 通过负载均衡器路由 | Nginx、AWS ALB |

##### 4.2 通信模式

| 模式     | 说明          | 适用场景       |
| :------- | :------------ | :------------- |
| 同步REST | HTTP请求-响应 | 简单查询       |
| 同步gRPC | 高性能RPC     | 服务间高频调用 |
| 异步消息 | 消息队列      | 解耦、削峰     |
| 事件驱动 | 事件总线      | 最终一致性     |

#### 5. 数据管理

##### 5.1 数据库每服务一个

```
用户服务 → 用户数据库
订单服务 → 订单数据库
商品服务 → 商品数据库
```

##### 5.2 分布式事务

| 模式       | 一致性   | 复杂度 | 适用场景     |
| :--------- | :------- | :----- | :----------- |
| 2PC        | 强一致   | 高     | 传统企业应用 |
| TCC        | 最终一致 | 高     | 金融场景     |
| Saga       | 最终一致 | 中     | 长事务       |
| 本地消息表 | 最终一致 | 低     | 简单场景     |

**Saga模式**：

```
正向: T1 → T2 → T3 → 完成
补偿: T1⁻¹ ← T2⁻¹ ← T3失败
```

## 8. 工程实践

本节把《微服务架构》放入真实工程场景，给出可复用的模式与组织方法。

演进：绞杀者模式（渐进替换）、 strangler fig。

### 8.1 工程实践的原则拆解

以上工程实践可以归纳为四条原则。第一，配置与代码分离：软件架构 项目中环境差异应通过配置注入，而不是散落在代码分支中；这保证同一份代码可以在开发、测试、生产环境一致运行。

第二，接口稳定优先：对外接口（函数签名、协议、数据格式）一旦被消费方依赖，变更成本极高；设计时应预留扩展点并保持向后兼容。

第三，可观测性内置：日志、指标与追踪应该在功能开发时同步设计，而不是故障发生后补救；没有观测手段的模块等于黑盒。

第四，变更可回滚：任何发布都应有对应的回滚方案；数据库迁移、配置变更与代码发布一样需要版本管理与逆向路径。
